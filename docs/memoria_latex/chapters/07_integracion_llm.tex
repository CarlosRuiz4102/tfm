\chapter{Integración de modelos de lenguaje}

\section{Papel del LLM en el sistema}

El sistema incorpora modelos de lenguaje como componentes especializados dentro de un flujo de análisis financiero histórico. El modelo no se utiliza como fuente directa de precios, como asesor financiero ni como mecanismo de predicción. Su función es transformar lenguaje natural en planificación analítica, generar código bajo contrato y redactar una explicación final a partir de resultados ya calculados.

La arquitectura actual distingue tres agentes:

\begin{itemize}
    \item \textbf{Agente 1: planificación}. Interpreta la petición del usuario, identifica el nivel de análisis A/B/C y define métricas, columnas, tablas o datos visuales que deben obtenerse.
    \item \textbf{Agente 2: generación de código}. Transforma el plan analítico en un script Python autocontenido, limitado por un contrato de entrada, salida e importaciones permitidas.
    \item \textbf{Agente 3: interpretación}. Recibe únicamente resultados calculados y redacta una explicación en español, separando datos históricos, lectura y limitaciones, sin recomendaciones de inversión.
\end{itemize}

Esta división evita que una única respuesta generativa mezcle planificación, cálculo y redacción. El modelo puede adaptar el sistema a consultas distintas, pero las cifras que llegan al usuario proceden de una ejecución programática sobre CSV locales.

\section{Contrato de prompts}

Los prompts se diseñan como contratos operativos. El agente planificador debe devolver JSON con el nivel A/B/C, el objetivo analítico, el tipo de análisis, las métricas requeridas, las columnas necesarias y los requisitos de salida. No calcula cifras y no redacta conclusiones.

El agente generador devuelve un único campo \texttt{code}. El script generado debe leer un payload JSON por \texttt{argv[1]}, cargar los datos mediante utilidades autorizadas, calcular las métricas necesarias y escribir un único JSON por \texttt{stdout}. No puede descargar datos externos, crear procesos, usar rutas no recibidas ni imprimir texto libre. Si la consulta pide tablas o datos visuales, el script debe devolverlos como estructuras JSON, no como imágenes.

El agente interpretador recibe la salida ejecutada y el plan. Su prompt prohíbe recalcular, completar cifras ausentes o añadir información externa. La respuesta debe ajustar su profundidad al nivel A/B/C, explicar las métricas observadas y declarar limitaciones cuando existan datos insuficientes.

\section{Niveles A/B/C}

El nivel de análisis no se recibe como etiqueta externa. Lo decide el agente de planificación a partir de la consulta:

\begin{itemize}
    \item \textbf{Nivel A}: petición directa, sin formato especial. Requiere métricas esenciales y una respuesta breve.
    \item \textbf{Nivel B}: análisis más completo, comparación clara, tabla o una salida visual principal. Requiere varias métricas y estructura tabular cuando proceda.
    \item \textbf{Nivel C}: petición profesional, multicriterio o con formato impuesto. Requiere varias familias de métricas, tablas, datos visuales si se solicitan y limitaciones explícitas.
\end{itemize}

Esta graduación permite exigir más al modelo sin convertir todas las consultas en informes extensos. También facilita la evaluación: un fallo puede localizarse en la planificación del nivel, en el código generado, en la ejecución o en la interpretación.

\section{Cliente compatible con Chat Completions}

La integración usa un cliente compatible con la interfaz de Chat Completions. OpenAI denomina \textit{Chat Completions} al endpoint que genera una respuesta del modelo a partir de una lista de mensajes que forman una conversación \cite{openaiChatCompletionsApi}. En este proyecto, la expresión describe el formato de interacción basado en mensajes y la forma de invocar el modelo desde el cliente.

El modelo principal del sistema es \texttt{openai/gpt-oss-20b} servido sobre vLLM. vLLM actúa como servidor de inferencia compatible con la interfaz de mensajes, mientras que el modelo evaluado y documentado sigue siendo \texttt{openai/gpt-oss-20b}. Esta distinción evita confundir el modelo con la infraestructura que lo expone.

\section{Gestión de errores}

El flujo registra errores de configuración, red, cuota, formato JSON, validación de código, ejecución e interpretación. Cada tipo de error se conserva en el estado del workflow para distinguir problemas de entorno, problemas del modelo y problemas del contrato técnico.

Si el agente de planificación o generación devuelve JSON no parseable, el sistema solicita una nueva respuesta estructurada. Si el código falla o no supera la validación de seguridad, puede pedirse una reparación al modelo, pero el script reparado vuelve a pasar por los mismos controles antes de ejecutarse. Esta decisión evita que la reparación sea una vía para saltarse el contrato.

\section{Credenciales y despliegue}

Las credenciales se gestionan mediante variables de entorno locales. El fichero de configuración real no debe versionarse ni compartirse. La configuración mínima requiere la URL del servidor vLLM, una clave del endpoint y el nombre \texttt{openai/gpt-oss-20b}. El código acepta también aliases compatibles con OpenAI para reutilizar el SDK, pero la configuración de referencia del proyecto es vLLM.
