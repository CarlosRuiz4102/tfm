\chapter{Integración del modelo de lenguaje}

El modelo de lenguaje interviene en tres momentos del flujo: comprende la consulta, genera el código necesario y explica los resultados calculados. Aunque estas funciones se presentan como tres agentes, la implementación utiliza el mismo modelo con instrucciones, entradas y formatos de salida diferentes. Por tanto, no se trata de tres modelos entrenados por separado, sino de tres roles especializados dentro de una misma arquitectura.

Esta separación resulta útil porque las tres tareas persiguen objetivos distintos. Planificar exige entender la intención del usuario; generar código requiere precisión técnica; e interpretar resultados demanda claridad y prudencia. Reunirlas en una única llamada reduciría el número de interacciones, pero dificultaría revisar qué decisión se tomó en cada momento y dónde se originó un posible error.

\section{Papel del modelo y división de responsabilidades}

El modelo actúa como enlace entre el lenguaje natural y las partes deterministas del sistema. Se utiliza allí donde una regla fija resulta insuficiente: interpretar qué solicita el usuario, decidir qué métricas son pertinentes, adaptar el código al caso y redactar una explicación proporcionada.

En cambio, no funciona como fuente de precios ni como mecanismo de cálculo implícito. Tampoco puede descargar información, incorporar noticias, predecir movimientos futuros o formular recomendaciones de inversión. Las cifras que llegan al usuario deben proceder del código ejecutado sobre los CSV proporcionados.

Los agentes se diferencian por la transformación que realizan:

\begin{itemize}
    \item el agente planificador convierte una petición abierta en un plan verificable;
    \item el agente generador convierte ese plan en código ejecutable;
    \item el agente interpretador convierte resultados estructurados en una explicación comprensible.
\end{itemize}

El primer agente concreta la intención; el segundo, el cálculo; y el tercero, la comunicación. Entre ellos se sitúan las validaciones y la ejecución descritas en el capítulo anterior.

La elección de estos tres roles responde a la decisión arquitectónica expuesta en el capítulo de diseño. No se busca simular un equipo de modelos diferentes, sino separar transformaciones que conviene poder revisar de forma independiente. El plan funciona como contrato entre la consulta y el código; los resultados ejecutados separan el cálculo de su explicación; y la respuesta final queda vinculada a unas evidencias concretas. Esta organización permite utilizar instrucciones más precisas para cada tarea y atribuir un posible fallo a la etapa en la que realmente se produjo.

\section{Diseño común de los prompts}

Los tres agentes comparten una instrucción de sistema que delimita el ámbito de actuación. El modelo debe comportarse como un componente de análisis financiero histórico y trabajar exclusivamente con la información proporcionada. Se prohíben los datos externos, las predicciones, el asesoramiento financiero y las recomendaciones de compra o venta.

El núcleo de esta instrucción puede resumirse en el siguiente fragmento:

\begin{quote}
\small
\textit{Trabajas exclusivamente con datos históricos ya disponibles en CSV y con el contrato JSON indicado. No realizas predicciones, asesoramiento de inversión, recomendaciones de compra o venta ni incorporas información que no esté en la entrada.}
\end{quote}

La misma idea se adapta después a cada tarea. El planificador no debe calcular cifras; el generador no redacta la respuesta final; y el interpretador no puede recalcular ni completar valores ausentes. Las restricciones se repiten de forma deliberada para que cada llamada sea comprensible por sí misma y no dependa de que el modelo recuerde una interacción anterior.

Los prompts combinan cuatro elementos:

\begin{enumerate}
    \item una definición clara del rol;
    \item la información disponible para esa etapa;
    \item el formato exacto que debe devolverse;
    \item las operaciones permitidas y prohibidas.
\end{enumerate}

En el cuerpo principal se recogen los fragmentos que mejor muestran estas diferencias. Las plantillas completas, sin los valores variables que se insertan en cada consulta, se incluyen en los anexos.

\section{Prompts específicos de los agentes}

\subsection{Agente 1: planificación analítica}

El primer agente recibe la consulta completa y la entrada estructurada. Su función consiste en decidir qué debe analizarse, no en realizar el cálculo. Debe identificar el objetivo financiero, seleccionar las métricas, indicar las columnas necesarias y anticipar cómo debería organizarse el resultado.

La instrucción principal establece:

\begin{quote}
\small
\textit{Tu tarea es convertir la petición del usuario en un plan verificable para un código Python posterior. No calcules cifras y no redactes la respuesta final.}
\end{quote}

La salida es un objeto JSON con el nivel de análisis, el objetivo, las métricas, las columnas requeridas, las necesidades de datos, los requisitos de salida y las preferencias de presentación. También incluye una justificación breve. Esta última no pretende obtener una cadena de pensamiento extensa, sino dejar constancia de por qué se eligieron ese nivel y esas métricas.

El prompt evita objetivos vagos. En lugar de indicar simplemente que se realizará un análisis, el agente debe concretar si necesita rentabilidad, volatilidad, drawdown, correlación, medias móviles, rankings temporales u otras medidas relacionadas con la consulta.

También diferencia las métricas de la forma de presentarlas. Una tabla comparativa o una serie normalizada no son cálculos por sí mismos, sino maneras de organizar los resultados. Esta separación ayuda a que el siguiente agente prepare una salida coherente.

\subsection{Agente 2: generación de código}

El segundo agente recibe la consulta original, la entrada validada, las rutas de los CSV y el plan analítico. No recibe los datos ya normalizados: la carga se realiza posteriormente, cuando se ejecuta el código mediante las utilidades comunes del proyecto.

Este agente está sometido al contrato más restrictivo. Su respuesta debe ser JSON y contener un único campo con el código completo. No se aceptan explicaciones, fragmentos parciales ni bloques Markdown. El fragmento central del prompt indica:

\begin{quote}
\small
\textit{Devuelve exclusivamente un objeto JSON válido con un único campo \texttt{code}. El valor debe ser un código Python completo y ejecutable. Debe leer la entrada indicada, calcular solo con los CSV recibidos y escribir un único JSON como resultado.}
\end{quote}

Además, el código debe utilizar las funciones comunes de carga, limitarse a las bibliotecas autorizadas, evitar el acceso a red y controlar datos ausentes, divisiones por cero y problemas de serialización. Si una métrica no puede calcularse, debe devolver un valor nulo y explicar la limitación en lugar de inventar un resultado.

Las exigencias cambian según la profundidad del plan. Una consulta A suele necesitar las métricas esenciales y un resumen. Los niveles B y C pueden requerir tablas, comparaciones, rankings o datos preparados para una representación visual. Incluso en estos casos, la salida debe mantenerse procesable y evitar series innecesariamente extensas.

La diferencia respecto al agente interpretador es clara: el generador no escribe para el usuario. Su prioridad es producir un cálculo correcto, estructurado y revisable.

\subsection{Reparación del código generado}

Cuando el código no supera la validación o falla durante el cálculo, puede realizarse una llamada de reparación. Esta conserva el mismo rol, pero añade la versión anterior y el error observado.

\begin{quote}
\small
\textit{El código anterior falló o fue rechazado. Devuelve una versión completa, no un parche parcial. Corrige la causa indicada y mantén el objetivo, el nivel y las salidas solicitadas por el plan.}
\end{quote}

La corrección no evita ningún control. La nueva versión vuelve a validarse y solo se ejecuta si cumple el mismo contrato que la primera. Como el modelo puede devolver otra respuesta incorrecta, el número de intentos se mantiene limitado y su resultado queda registrado.

\subsection{Agente 3: interpretación de resultados}

El tercer agente recibe el plan y la salida calculada. No vuelve a leer los CSV ni decide nuevas métricas. Su tarea consiste en seleccionar la información relevante, explicar su significado y adaptar la extensión a la petición.

Su instrucción principal cambia el formato exigido:

\begin{quote}
\small
\textit{Redacta la respuesta final usando únicamente los resultados y el plan analítico. No recalcules, no completes cifras ausentes y no incorpores datos externos. Devuelve texto en español con frases completas, no JSON ni bloques de código.}
\end{quote}

La respuesta debe distinguir entre datos históricos observados, lectura interpretativa y limitaciones. Si existe una tabla o una serie preparada para una representación visual, puede explicar qué muestra, pero no debe afirmar que se ha generado una imagen. Tampoco puede ocultar valores nulos o datos insuficientes.

La extensión se adapta al nivel identificado durante la planificación. Una respuesta A debe ser breve y directa; una B puede organizar varias métricas y comparaciones; y una C debe comportarse como un informe compacto, con apartados claros cuando la consulta los requiera.

La clasificación no depende únicamente del número de activos. Una consulta sobre un solo instrumento puede pertenecer al nivel C si exige varias familias de riesgo, datos de evolución y una organización concreta. Del mismo modo, una comparación entre dos activos puede mantenerse en el nivel A si solo pregunta cuál obtuvo mayor rentabilidad.

El prompt utiliza señales como la solicitud de tablas, series normalizadas, drawdown, medias móviles, rankings, periodos extremos o bloques obligatorios. Estas referencias ayudan a mantener un criterio estable, aunque la decisión final debe atender al conjunto de la petición.

\section{Procesamiento de respuestas y gestión de errores}

Las respuestas del planificador y del generador deben poder procesarse automáticamente. El sistema elimina envoltorios de formato cuando aparecen y busca un objeto JSON válido. Si encuentra texto adicional alrededor, intenta recuperar únicamente el fragmento estructurado.

Cuando la respuesta no puede analizarse, se realiza un nuevo intento con una indicación más directa: devolver exclusivamente JSON válido, sin explicaciones ni Markdown. El número de intentos está limitado. En la generación de código también se admite una recuperación acotada cuando el modelo devuelve directamente un programa reconocible, aunque no haya respetado por completo el envoltorio solicitado.

La interpretación sigue la lógica contraria. Su resultado debe ser texto natural. Si el modelo devuelve únicamente JSON, se solicita una nueva respuesta que explique los valores mediante frases completas. Esto refleja una decisión central: la estructura se reserva para coordinar las etapas internas y el texto libre para la comunicación final.

Los errores pueden aparecer en cualquiera de los roles. El planificador puede devolver un formato incompleto o seleccionar métricas poco adecuadas; el generador puede producir JSON inválido, código con errores sintácticos u operaciones rechazadas; y el interpretador puede devolver texto vacío, repetir la estructura recibida o redactar una explicación insuficiente.

La aplicación conserva el punto en el que apareció el problema. Así puede distinguirse un fallo de comunicación con el servicio, una respuesta mal formada, un rechazo técnico, un error durante los cálculos o una interpretación que no llegó a completarse. Los resultados concretos de estos comportamientos se presentan en el capítulo de evaluación.

\section{Cliente, modelo y configuración}

La integración utiliza un cliente compatible con la interfaz de mensajes de Chat Completions. Cada petición se representa mediante una secuencia de mensajes con distintos roles y el modelo devuelve una respuesta asociada a esa conversación~\cite{openaiChatCompletionsApi}. El sistema construye una conversación independiente para cada agente, formada por la instrucción común y el mensaje específico de la tarea.

El modelo evaluado es \texttt{openai/gpt-oss-20b}, un modelo de pesos abiertos documentado por OpenAI~\cite{openai2025gptossmodelcard}. Durante las pruebas se accede a él mediante un servidor vLLM compatible con la interfaz del cliente. Conviene separar ambos conceptos: el modelo aporta la capacidad generativa y vLLM proporciona la infraestructura de inferencia.

La configuración permite indicar la dirección del servicio, el nombre del modelo, el tiempo máximo de respuesta, la temperatura y el límite de tokens. Se utiliza una temperatura baja para reducir variaciones innecesarias, aunque el comportamiento continúa siendo generativo y una única ejecución no elimina la posibilidad de obtener respuestas distintas.

\section{Alcance de la estrategia de prompts}

Los prompts se han ajustado de forma incremental a partir de los problemas encontrados durante el desarrollo. Los formatos estructurados, las utilidades comunes de carga, las reglas de serialización y los recordatorios sobre datos insuficientes responden a dificultades observadas en las primeras pruebas.

Estas instrucciones mejoran la estabilidad, pero no garantizan que todas las respuestas sean correctas. Un prompt orienta al modelo; no constituye una verificación formal. Por esa razón, las salidas se combinan con controles deterministas y se conservan los productos intermedios.

La división en tres agentes tampoco es la única arquitectura posible. Una sola llamada reduciría coste y latencia, pero ofrecería menos puntos de control y ocultaría parte del recorrido seguido por el modelo. Para el propósito de este trabajo, la separación resulta adecuada porque permite evaluar de forma diferenciada la comprensión, la generación de código y la redacción, además de localizar con mayor precisión el origen de los fallos.

En conjunto, la integración busca aprovechar la flexibilidad del LLM sin convertirlo en la única fuente de control. Los prompts delimitan cada tarea, los contratos conectan las etapas y la validación externa decide si sus productos pueden utilizarse.
