\section{Ejecución del MVP}

El prototipo puede ejecutarse con ejemplos incluidos en el repositorio:

\begin{verbatim}
python run_mvp.py --example growth_nvda
python run_mvp.py --example compare_nvda_amd
python run_mvp.py --example overview_aapl
python run_mvp.py --example returns_qqq_spy
python run_mvp.py --example risk_qqq_spy
python run_mvp.py --example technical_aapl
\end{verbatim}

También puede recibir un JSON de entrada con consulta, tickers, fechas o periodo, intervalo y rutas a CSV locales.

\section{Configuración de API}

Las claves de API se guardan localmente en el fichero \texttt{.env}, que no debe subirse al repositorio. La configuración mínima es:

\begin{verbatim}
OPENAI_API_KEY=...
VLLM_BASE_URL=https://servidor-vllm.example/v1
VLLM_API_KEY=...
VLLM_MODEL=openai/gpt-oss-20b
\end{verbatim}

Si el modelo de OpenAI se sirve desde un servidor vLLM compatible con la interfaz de mensajes, puede indicarse una URL base:

\begin{verbatim}
OPENAI_BASE_URL=https://servidor-vllm.example/v1
OPENAI_MODEL=openai/gpt-oss-20b
\end{verbatim}

En este caso, vLLM describe la infraestructura que sirve el modelo; el modelo sigue identificándose como modelo de OpenAI \cite{openai2025gptossmodelcard}.

\section{Prompts usados por los agentes}

El prompt base define un componente profesional de análisis financiero histórico. Todos los agentes comparten las mismas restricciones: trabajar sólo con datos históricos disponibles en CSV, no predecir, no recomendar inversión y no añadir información externa.

\subsection{Agente 1: planificación}

El agente planificador devuelve JSON con nivel A/B/C, objetivo analítico, tipo de análisis, métricas, columnas requeridas, requisitos de datos, requisitos de salida y una justificación breve del nivel elegido. No calcula cifras y no redacta la respuesta final.

\subsection{Agente 2: generación de código}

El agente generador devuelve un JSON con un único campo \texttt{code}. El script debe leer el payload desde \texttt{argv[1]}, cargar datos mediante funciones autorizadas, calcular métricas sobre CSV locales y emitir un único JSON por \texttt{stdout}. Si se solicitan datos visuales, se devuelven como estructuras JSON, no como ficheros de imagen.

\subsection{Agente 3: interpretación}

El agente interpretador recibe la salida ejecutada y el plan. Su tarea es explicar los resultados en español, ajustando la profundidad al nivel A/B/C y separando datos históricos, lectura y limitaciones. No recalcula ni incorpora datos externos.

\section{Trazabilidad de una ejecución}

Cada ejecución conserva la entrada normalizada, el plan analítico, el código generado, la salida estándar, los errores y la respuesta final. Estos artefactos permiten repetir una prueba, revisar qué entendió cada agente y comprobar si la interpretación final se corresponde con los resultados calculados.

\section{Métricas subjetivas futuras}

La revisión subjetiva de calidad se mantiene como línea futura. La plantilla prevista incluye comprensión de la consulta, selección de métricas, adecuación del código, fidelidad a resultados, claridad, utilidad, reconocimiento de limitaciones, ausencia de recomendación de inversión y trazabilidad. Antes de usar estas métricas como evidencia principal será necesario reforzar la rúbrica y definir criterios de revisión más estables.
