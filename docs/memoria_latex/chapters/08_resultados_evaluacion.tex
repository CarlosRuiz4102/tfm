\chapter{Resultados y evaluación}

\section{Objetivo}

La evaluación comprueba si el prototipo mantiene el flujo completo al aumentar la dificultad de las consultas. No busca demostrar capacidad predictiva ni establecer un ranking de servicios LLM. El foco está en verificar planificación, generación de código, validación, ejecución e interpretación final sobre datos históricos locales.

\section{Métricas técnicas}

La evaluación se apoya en métricas técnicas registrables:

\begin{itemize}
    \item \textbf{Completitud}: estado final \texttt{completed}.
    \item \textbf{Plan generado}: existencia de un plan A/B/C parseable.
    \item \textbf{Código generado}: existencia de script que cumple el contrato mínimo.
    \item \textbf{Código validado}: superación de la revisión de seguridad.
    \item \textbf{Ejecución correcta}: retorno cero y salida JSON parseable.
    \item \textbf{Interpretación final}: respuesta en español basada en resultados calculados.
    \item \textbf{Prudencia financiera}: ausencia de recomendaciones de compra o venta.
    \item \textbf{Tiempo de ejecución}: duración observada por caso.
\end{itemize}

Las métricas subjetivas, como claridad percibida, utilidad o calidad comunicativa, quedan previstas para una fase posterior. Se consideran relevantes, pero deben reforzarse con una rúbrica más estable y revisores consistentes antes de tratarlas como evidencia principal.

\section{Resultados observados}

La versión actual del prototipo se orienta a \texttt{openai/gpt-oss-20b} servido sobre vLLM. vLLM se interpreta como el servidor de despliegue compatible, no como un proveedor alternativo del estudio.

La evaluación registra para cada caso si el flujo llega a planificar, generar código, validar, ejecutar e interpretar. Los casos parciales son informativos porque permiten localizar el punto de fallo. Por ejemplo, un caso con plan correcto pero ejecución fallida señala un problema distinto a un caso que no llega a producir JSON válido en la primera llamada LLM.

\section{Limitaciones}

Una única pasada de evaluación no permite afirmar robustez estadística. La disponibilidad del modelo, la cuota, la latencia y la estabilidad del endpoint pueden afectar a los resultados. Además, la generación de código mediante LLM requiere validación estricta porque una solución plausible puede fallar por detalles de formato, columnas, datos insuficientes o serialización.

El sistema trabaja con datos históricos locales. No incorpora noticias, datos fundamentales ni precios actuales externos. Por tanto, las respuestas deben leerse como análisis descriptivos del periodo disponible, no como predicciones ni recomendaciones de inversión.

\section{Síntesis}

La evaluación muestra un prototipo funcional y trazable. La contribución principal es que el sistema no mide sólo si el texto final parece útil, sino si cada fase produce artefactos verificables: plan, código, validación, ejecución y explicación. La batería A/B/C permite aumentar la exigencia de forma ordenada y deja preparadas métricas subjetivas que podrán reforzarse en trabajo futuro.
