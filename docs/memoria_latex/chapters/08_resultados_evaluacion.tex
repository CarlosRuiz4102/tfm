\chapter{Resultados y evaluación}

Este capítulo recoge la evaluación del prototipo desarrollado con foco en resultados generados mediante LLM y código Python ejecutado de forma controlada. El objetivo no es demostrar que el sistema prediga el mercado, sino comprobar si la arquitectura interpreta consultas, genera código, valida su seguridad, ejecuta métricas históricas y redacta conclusiones comprensibles.

\section{Protocolo de evaluación}

La evaluación se ha diseñado alrededor de consultas representativas de análisis financiero histórico: crecimiento de precio, comparación de activos, visión descriptiva, análisis de retornos, análisis de riesgo histórico y análisis técnico. Para cada ejecución se registran el estado final, la interpretación estructurada, el código de retorno del script, el tiempo de ejecución, los avisos, la salida JSON y la respuesta final.

La lectura de resultados debe interpretarse teniendo en cuenta la evolución del MVP. Las primeras pruebas se centraron en comprobar dos intencionalidades básicas, crecimiento y comparación. Después se amplió la batería a seis intencionalidades para validar una cobertura funcional más amplia. La fase actual incorpora comparación entre modelos, niveles cualitativos de profundidad y queries de estrés visual que obligan al sistema a producir tablas, datos para gráficas y conclusiones explicativas.

El proyecto contempla tres perfiles de ejecución: Groq con \nolinkurl{llama-3.3-70b-versatile}, Gemini con \nolinkurl{gemini-2.5-flash} y el perfil técnico \texttt{university}, que corresponde a \nolinkurl{openai/gpt-oss-20b} servido mediante vLLM en el entorno universitario. En todos los casos el workflow usa el modelo configurado para interpretación de consulta, generación de código e interpretación final. Si falta una clave, el modelo no está disponible, el código se rechaza o la ejecución falla, el caso queda marcado como error controlado.

\section{Métricas y criterios de evaluación}

Las métricas técnicas utilizadas son:

\begin{itemize}
    \item \textbf{Casos funcionales completados}: número de consultas válidas que terminan con estado \texttt{completed}.
    \item \textbf{Errores controlados}: número de consultas inválidas o fallidas que terminan con explicación.
    \item \textbf{Errores LLM}: problemas de configuración, red, cuota, disponibilidad, contexto o formato.
    \item \textbf{Código rechazado}: scripts que no superan el contrato de seguridad.
    \item \textbf{Violaciones de recomendación de inversión}: presencia de expresiones como comprar, vender o recomendar invertir.
    \item \textbf{Tiempo de ejecución}: duración observada por caso y proveedor.
\end{itemize}

A estas métricas se añade una revisión cualitativa, porque la completitud técnica no garantiza por sí sola que el análisis sea útil. La revisión humana valora comprensión de la consulta, selección de métricas, suficiencia del código generado, adecuación de tablas o gráficas, exactitud respecto a los datos ejecutados, claridad del texto final, reconocimiento de limitaciones y ausencia de recomendaciones de inversión. Esta decisión es coherente con la necesidad de explicar cómo se calcula y presenta el rendimiento histórico \cite{investorgov2022performanceclaims}, y con la separación entre retorno, riesgo, volatilidad y correlación como conceptos de análisis histórico \cite{investorgov2026risk,cfainstitute2026portfolioriskreturn}.

\section{Niveles cualitativos de salida}

La evaluación cualitativa se estructura en tres niveles:

\begin{itemize}
    \item \textbf{Nivel A}: consultas simples sin requisitos de presentación. La respuesta esperada es breve y debe incluir métricas básicas suficientes.
    \item \textbf{Nivel B}: consultas que piden un análisis más completo. La respuesta esperada incluye texto, tabla de métricas y una gráfica principal o datos estructurados para generarla.
    \item \textbf{Nivel C}: consultas profesionales o detalladas. La respuesta esperada incluye varias salidas estructuradas, por ejemplo tabla, evolución normalizada, drawdown, ranking mensual, desglose de riesgo o conclusión ejecutiva.
\end{itemize}

El uso de visualizaciones depende de la intención de la consulta. Para series temporales se priorizan gráficos de línea y, cuando se comparan activos con escalas distintas, una evolución normalizada permite comparar la tendencia sin confundir niveles de precio absolutos. También se evita abusar de demasiadas series o ejes dobles, porque pueden dificultar la lectura \cite{atlassianlinecharts}. En consultas de riesgo se considera especialmente útil el drawdown, ya que resume caídas históricas desde máximos previos y se entiende con facilidad \cite{cfainstitute2018drawdown}.

\section{Batería progresiva de evaluación}

Para comprobar la amplitud del TFM se utilizaron queries de dificultad creciente. La batería completa documentada incluye doce queries A/B/C; para la comparación multi-modelo se seleccionó una muestra progresiva de cinco casos:

\begin{itemize}
    \item \texttt{level\_a\_nvda\_growth}: crecimiento simple de NVDA.
    \item \texttt{level\_a\_qqq\_spy\_returns}: retornos históricos de QQQ y SPY.
    \item \texttt{level\_b\_qqq\_spy\_clear\_compare}: comparativa con tabla y gráfica normalizada.
    \item \texttt{level\_c\_qqq\_spy\_professional}: análisis profesional con tabla, normalización, drawdown y conclusión.
    \item \texttt{stress\_visual\_qqq\_spy\_monthly}: query de estrés visual con cuatro bloques obligatorios: tabla resumen, ranking mensual, gráfica normalizada y gráfica de drawdown.
\end{itemize}

La query de estrés visual es especialmente relevante porque obliga al primer agente a generar datos de forma concreta y al segundo agente a respetar una estructura de comunicación para cliente no técnico. El texto usado fue:

\begin{quote}
Compara QQQ y SPY durante 2024 como si fuera un informe para un cliente no técnico. Quiero que me muestres los datos exactamente en cuatro bloques: 1) una tabla resumen con rentabilidad total, volatilidad anualizada, máximo drawdown, mejor mes y peor mes; 2) una tabla ranking mensual indicando que activo ganó cada mes; 3) datos para una gráfica normalizada base 100 de ambos activos; 4) datos para una gráfica de drawdown. Cierra con una conclusión clara, sin recomendar comprar ni vender.
\end{quote}

\section{Análisis de la query de estrés visual}

La query de estrés visual permitió comprobar si el sistema podía respetar una salida impuesta por el usuario. Con el perfil universitario, el workflow completo llegó a estado \texttt{completed}. La salida estructurada incluyó rentabilidad total, volatilidad anualizada, drawdown, ranking mensual y datos para representaciones normalizadas y de drawdown. El resultado principal fue que QQQ obtuvo mayor rentabilidad histórica en 2024, mientras que SPY presentó un perfil más estable.

El ranking mensual calculado mostró una alternancia razonable: QQQ destacó en varios meses alcistas, mientras que SPY se comportó mejor en meses donde su menor volatilidad favoreció la comparación. Este tipo de caso muestra por qué la evaluación cualitativa es necesaria: no basta con que el modelo devuelva un número, sino que debe organizar datos de forma comprensible para el cliente.

\section{Fallos observados y mejoras derivadas}

Los errores observados durante la evaluación fueron técnicamente útiles:

\begin{itemize}
    \item \textbf{Cuotas de proveedor}: Groq y Gemini devolvieron errores \texttt{429} al superar límites de uso. Estos fallos no invalidan la arquitectura, pero condicionan la comparación experimental.
    \item \textbf{Contexto excesivo}: algunas salidas visuales incluían series demasiado largas. Esto provocaba errores de contexto en el segundo agente.
    \item \textbf{Formato JSON}: en algunos casos el modelo entendía bien la query, pero fallaba al devolver código dentro de JSON válido.
    \item \textbf{Reparación de código}: algunas ejecuciones requirieron reparación automática antes de producir una salida válida.
\end{itemize}

A partir de estos problemas se incorporó compactación de salidas antes de la interpretación final. La salida completa permanece guardada en artefactos, pero el segundo agente recibe una versión resumida de listas y textos largos. Esta decisión mantiene trazabilidad y reduce errores por límite de contexto.

\section{Limitaciones}

La evaluación aún presenta limitaciones. El número de casos es reducido para afirmar robustez estadística. La calidad de las respuestas LLM requiere revisión humana y las cifras de latencia dependen de red, cuota y carga del proveedor. Además, la evaluación cualitativa incorpora juicio humano, por lo que debe entenderse como una comparación exploratoria apoyada en criterios previamente definidos, no como una medición objetiva absoluta.

También debe distinguirse entre resultados observados y resultados pendientes de repetición. La pasada progresiva completa quedó condicionada por cuotas diarias, especialmente en Groq y Gemini. Por ello se conserva el informe actual como evidencia de comportamiento real, pero se propone repetir la evaluación con cuotas disponibles para obtener una comparación más equilibrada.

\section{Síntesis}

Los resultados respaldan la hipótesis de diseño: una arquitectura LLM con ejecución controlada puede transformar consultas financieras estructuradas en código, métricas, datos visuales y explicaciones trazables. La evaluación por niveles A/B/C muestra que el sistema responde a consultas simples, escala hacia análisis con tablas y gráficas, y puede abordar peticiones profesionales o de estrés visual. La aportación principal es separar interpretación, generación de código, validación, ejecución e interpretación final, permitiendo revisión humana posterior y documentación clara de fallos.
