NOTAS TECNICAS DEL TFM - SISTEMA MULTIAGENTE ANALISTA
=====================================================

0. OBJETIVO REAL DEL DESARROLLO
-------------------------------
No hay que construir desde cero un sistema que entienda lenguaje natural completo,
porque esa parte ya esta resuelta.

La entrada del sistema ya sera:
- query estructurada
- intencion
- tickers
- fechas o periodo
- intervalo
- rutas a los CSV

Por tanto, el trabajo nuevo consiste en construir un pipeline que:
1. valide esa entrada
2. decida que analisis corresponde
3. genere un plan analitico
4. genere codigo Python
5. ejecute ese codigo
6. devuelva un resultado interpretable

En una frase:
El TFM no va de parsear la query, sino de orquestar el analisis.


1. IDEA GENERAL DE LA ARQUITECTURA
----------------------------------
Separar el sistema en 3 capas:

CAPA 1. ORQUESTACION
- Libreria principal: LangGraph
- Funcion: organizar el flujo del sistema

CAPA 2. GENERACION CON LLM
- Libreria/infraestructura: vLLM
- Funcion: servir el modelo que usaran algunos nodos

CAPA 3. EJECUCION DE CODIGO
- Libreria: subprocess
- Funcion: ejecutar el script Python generado y capturar resultados

Resumen:
- LangGraph organiza
- vLLM responde como modelo
- subprocess ejecuta el analisis real


2. QUE DEBE HACER LANGGRAPH EN ESTE PROYECTO
--------------------------------------------
LangGraph debe representar el workflow del sistema.
No debe rehacer el parser de query ni la descarga de datos.
Debe arrancar desde la entrada estructurada ya disponible.

Su papel principal sera:
- mantener un estado compartido
- ejecutar nodos
- decidir transiciones entre nodos
- enrutar por intencion
- manejar errores

Flujo conceptual:

query estructurada + csv_paths
-> ingest
-> router/orchestrator
-> specialist_analysis
-> code_generation
-> code_execution
-> interpretation
-> output final


3. QUE DEBE HACER vLLM EN ESTE PROYECTO
---------------------------------------
vLLM NO organiza el pipeline.
vLLM NO decide el flujo.
vLLM solo sirve el modelo.

Su papel es:
- exponer el LLM con API compatible con OpenAI
- permitir que LangGraph o LangChain llamen al modelo
- responder a prompts de planning, codegen e interpretacion

Tareas donde SI usar el LLM:
- confirmar intencion si alguna vez llega ambigua
- generar plan analitico
- generar codigo Python
- interpretar el resultado final

Tareas donde NO usar el LLM:
- cargar CSV
- validar rutas de ficheros
- comprobar numero de tickers
- validar periodo o intervalo si ya esta normalizado
- ejecutar el script


4. QUE DEBE HACER SUBPROCESS
----------------------------
Subprocess se usara para ejecutar el codigo Python generado.

Funcion esperada:
- guardar el codigo en un archivo .py
- lanzar el script como proceso externo
- capturar stdout
- capturar stderr
- guardar returncode
- detectar si el script fallo o no

Reglas practicas:
- no usar shell=True
- usar lista de argumentos
- poner timeout
- guardar logs

Patron base:
subprocess.run(["python", script_path], capture_output=True, text=True, timeout=60, check=False)


5. INTENCIONES ANALITICAS DEFINIDAS
-----------------------------------
El sistema debe trabajar con estas 6 intenciones:

+-----------------------------+-----------------------------------------------+-----------------------------------------+
| INTENCION                   | OBJETIVO                                      | SALIDA ESPERADA                         |
+-----------------------------+-----------------------------------------------+-----------------------------------------+
| asset_overview              | vision general de un activo                   | resumen + metricas basicas + grafico    |
| price_growth                | crecimiento o caida en un periodo             | variacion absoluta y porcentual         |
| compare_assets              | comparacion entre varios activos              | comparacion normalizada + conclusiones  |
| return_analysis             | estudio de la serie de retornos               | retornos, medias, extremos              |
| historical_risk_analysis    | riesgo historico, no predictivo               | volatilidad, drawdown, ratios simples   |
| technical_analysis          | indicadores tecnicos                          | indicadores, senales y graficos         |
+-----------------------------+-----------------------------------------------+-----------------------------------------+

Restriccion importante:
- no hacer prediccion futura
- no hacer forecasting
- no hacer sentiment con noticias
- no hacer fundamental analysis complejo


6. DECISION CLAVE DE DISENO
---------------------------
No empezar con 6 agentes totalmente separados desde el primer dia.

Empezar con un workflow controlado y pequeno:
- router/orchestrator
- specialist_analysis
- code_generator
- code_executor
- result_interpreter

Luego, cuando funcione el flujo general, dividir specialist_analysis en agentes por intencion.

Ventaja:
- menos complejidad inicial
- mas facil depurar
- mas facil saber donde falla
- mas rapido llegar a un MVP funcional


7. MVP RECOMENDADO
------------------
MVP = Minimum Viable Product
En este proyecto significa:
la version minima del pipeline que ya funciona de principio a fin.

MVP 1 recomendado:
- solo 2 intenciones: price_growth y compare_assets
- 1 solo nodo specialist_analysis
- 1 code_generation_node con prompt cerrado
- 1 code_execution_node
- 1 interpretation_node simple

Objetivo del MVP 1:
probar que el flujo entero funciona.

MVP 2:
- anadir asset_overview y return_analysis
- separar nodos especialistas por familia

MVP 3:
- anadir historical_risk_analysis y technical_analysis
- mejorar prompts
- mejorar evaluacion


8. ENTRADA QUE DEBE RECIBIR EL GRAFO
------------------------------------
Formato recomendado de entrada al workflow:

{
  "query": "Compara Nvidia y AMD en 2 anos",
  "intent": "compare_assets",
  "tickers": ["NVDA", "AMD"],
  "start": null,
  "end": null,
  "period": "2y",
  "interval": "1d",
  "csv_paths": [
    "data/raw/NVDA_2y_1d.csv",
    "data/raw/AMD_2y_1d.csv"
  ]
}

Idea clave:
LangGraph debe arrancar aqui.
No debe volver a inferir la query desde cero.


9. ESTADO COMPARTIDO MINIMO DEL GRAFO
-------------------------------------
El grafo debe compartir un estado comun entre nodos.

Campos minimos recomendados:

- user_query: str
- normalized_query: dict
- csv_paths: list[str]
- detected_intent: str
- selected_agent: str
- analysis_plan: dict
- generated_code: str
- execution_stdout: str
- execution_stderr: str
- execution_returncode: int
- final_answer: str
- warnings: list[str]

Idea practica:
Cada nodo lee parte del estado y devuelve nuevas claves o actualizaciones.


10. NODOS MINIMOS DEL WORKFLOW
------------------------------

10.1 ingest_node
----------------
Funcion:
- recibe la query estructurada y las rutas a CSV
- comprueba que existe la entrada minima
- verifica que las rutas existan

Usa:
- Python normal
- sin LLM

Salida:
- estado validado inicialmente
- errores simples si falta algo


10.2 orchestrator_router_node
-----------------------------
Funcion:
- valida coherencia de la peticion
- revisa intencion
- revisa numero de tickers
- revisa rango temporal / periodo / intervalo
- selecciona el agente o ruta siguiente

Usa:
- LangGraph
- Python normal
- opcionalmente LLM si algun dia hay ambiguedad

Salida:
- selected_agent
- warnings
- o salto a invalid_request_node


10.3 specialist_analysis_node
-----------------------------
Funcion:
- traduce la intencion a un plan de analisis concreto
- decide metricas, graficos, columnas necesarias y foco del analisis

Usa:
- LLM o mezcla de Python + LLM

Importante:
- no debe devolver texto libre ambiguo
- debe devolver una estructura clara

Ejemplo de salida:
{
  "intent": "compare_assets",
  "metrics": ["cumulative_return", "normalized_performance"],
  "plots": ["normalized_price_chart"],
  "required_columns": ["Date", "Close"]
}


10.4 code_generation_node
-------------------------
Funcion:
- convertir el plan analitico en codigo Python ejecutable

Usa:
- LLM

Reglas:
- prompt muy restringido
- imports controlados
- salida ideal: solo codigo o JSON con campo code
- debe trabajar sobre CSV reales del sistema


10.5 code_execution_node
------------------------
Funcion:
- guardar el script
- ejecutarlo con subprocess
- capturar stdout, stderr y returncode
- guardar resultados en results/

Usa:
- Python normal
- subprocess


10.6 interpretation_node
------------------------
Funcion:
- leer las metricas o salidas del script
- redactar la respuesta final
- resumir limitaciones o warnings

Usa:
- LLM o plantilla programatica


10.7 invalid_request_node
-------------------------
Funcion:
- manejar entradas mal construidas o inconsistentes


10.8 execution_error_node
-------------------------
Funcion:
- manejar errores de ejecucion del script generado

19. RIESGOS TECNICOS A VIGILAR
------------------------------
- vLLM puede ser lo mas dificil de instalar
- el codigo generado puede romper por columnas mal nombradas
- puede haber inconsistencias entre CSV esperado y CSV real
- un prompt demasiado libre puede generar codigo fragil
- la interpretacion final puede ser buena aunque la metrica este mal, por eso hay que validar antes

Medidas practicas:
- empezar con routing determinista
- usar prompts muy cerrados
- usar pocas intenciones al principio
- registrar todo en logs
- guardar scripts generados


20. RECOMENDACION TACTICA IMPORTANTE
------------------------------------
No bloquear el desarrollo esperando a tener vLLM perfecto.

Orden recomendado:
1. hacer funcionar LangGraph con un backend de modelo accesible
2. estabilizar workflow, prompts y ejecucion
3. sustituir despues el backend por vLLM si hace falta

La prioridad al principio no es el serving perfecto del modelo,
sino demostrar que el pipeline multiagente funciona.


21. PRIMER ENTREGABLE TECNICO UTIL
----------------------------------
Un notebook o script que reciba:
- una query estructurada
- uno o varios csv_paths

y devuelva:
- agente seleccionado
- plan analitico
- codigo generado
- stdout/stderr/returncode
- interpretacion final

Si eso funciona con 2 intenciones, ya hay una base muy valida del sistema.
