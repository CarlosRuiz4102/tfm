RESULTADOS DEL PROYECTO - TFM FINANCIAL MULTIAGENT MVP
======================================================

Fecha de preparacion: 14/05/2026
Proyecto: TFM Financial Multiagent MVP
Destinatarios: revision interna / empresa


RESUMEN EJECUTIVO
-----------------

El proyecto valida un MVP capaz de analizar datos financieros historicos mediante
un flujo controlado: validacion de la consulta, seleccion del agente, generacion
del plan analitico, ejecucion del codigo y redaccion de la respuesta final.

La conclusion principal es que el sistema funciona de forma estable sin depender
de modelos externos y, ademas, puede incorporar APIs LLM como una capa opcional
para mejorar la explicacion final. Esto permite combinar dos ventajas:

  [1] Calculo financiero determinista, trazable y reproducible.
  [2] Respuestas finales mas naturales cuando se activa un modelo LLM.

En las pruebas documentadas, los seis casos representativos del MVP se completan
correctamente en modo determinista, con Groq y con el modelo universitario vLLM.
Gemini tambien completa los casos tras reintento, aunque muestra limitaciones de
cuota y disponibilidad en el free tier.

de descarga.

El conjunto cubre distintos tipos de activo:

Esta variedad permite comprobar que el sistema no esta limitado a un unico tipo
de instrumento financiero y que puede trabajar con consultas diarias e intradia.

4. RESULTADOS POR PROPUESTA

Las propuestas evaluadas tienen un punto comun importante: el calculo financiero
permanece controlado por el pipeline del proyecto. Los modelos LLM, cuando se
activan, se usan solo para interpretar y redactar la respuesta final.

6. CONCLUSIONES CLAVE
---------------------

  1. El MVP no depende criticamente de un LLM.
     El modo determinista completa los seis casos y sirve como baseline y como
     fallback ante fallos externos.

  2. La mejor configuracion actual es hibrida.
     El calculo financiero queda en codigo controlado y el LLM se usa solo para
     redactar una explicacion final mas natural.

  3. Groq es el proveedor mas practico para continuar iterando.
     Completa los seis casos sin warnings y mejora la experiencia de lectura.

  4. Gemini aporta valor comparativo, pero requiere gestionar cuotas.
     Es util para demostrar portabilidad entre proveedores, aunque el free tier
     limita ejecuciones consecutivas.

  5. El modelo universitario vLLM queda validado.
     Completa los seis casos sin fallback ni warnings y confirma que la
     arquitectura puede conectarse a un backend academico propio.

  6. La separacion por fases reduce riesgo.
     No se delega al LLM ni la planificacion ni la generacion de codigo. Esto
     evita que el modelo altere metricas financieras o introduzca resultados no
     trazables.


7. RECOMENDACION FINAL
----------------------

Para la siguiente fase del proyecto se recomienda mantener esta configuracion:

  LLM_USE_FOR_PLANNING=false
  LLM_USE_FOR_CODEGEN=false
  LLM_USE_FOR_INTERPRETATION=true

Motivo:

  - Mantiene el calculo financiero bajo control.
  - Reduce el riesgo de alucinaciones en metricas.
  - Mejora la claridad de la respuesta final.
  - Permite cambiar de proveedor LLM sin redisenar el sistema.
  - Conserva el fallback determinista ante fallos de red, cuota o dependencia.

Orden recomendado de uso:

  [1] Determinista como base y fallback.
  [2] Groq como proveedor principal para pruebas LLM.
  [3] Universidad vLLM como backend academico validado.
  [4] Gemini como proveedor secundario para comparativas puntuales.


8. MENSAJE PARA PRESENTACION
----------------------------

El resultado del proyecto no es solo que el MVP responda consultas financieras,
sino que lo hace con una arquitectura robusta. Primero calcula de forma
determinista, despues interpreta los resultados y solo al final, si se desea,
usa un LLM para mejorar la redaccion.

Esto permite presentar el sistema como una solucion hibrida: fiable en el dato,
flexible en la explicacion y resistente ante fallos de proveedores externos.
